# GigGuard Admin Dashboard — Implementation Plan & Developer Guide

This document is a comprehensive guide to building the Admin Dashboard for the GigGuard (formerly GigShield) Insurtech platform. It explains the system architecture, how the backend calculates risk, stores data, evaluates fraud, and interfaces with the mobile frontend, along with specific requirements for the administrative interface.

## 1. System Architecture & Tech Stack

To maintain the premium insurtech aesthetic and ensure rapid development, the dashboard should be built with modern, performant web technologies:

* **Framework:** Next.js (React) or Vite + React
* **Styling:** Vanilla CSS or CSS Modules with a premium, sleek dark-mode aesthetic (evoking security and real-time intelligence).
* **Data Fetching:** SWR or React Query for real-time polling (essential for fraud and circuit-breaker monitoring).
* **Charts/Maps:** Recharts or Chart.js for analytics, and React-Leaflet / Mapbox for real-time rider tracking and geographical risk areas.
* **Authentication:** JWT-based (must tap into the existing backend auth flow or use a separate admin table).

## 2. Frontend Architecture Context (Mobile App)

The existing Rider application `MobileApp/` is built using **React Native & Expo**. As the Admin Dashboard developer, it is vital to understand the frontend paradigms you’ll be complementing:

* **State & Authentication:** The mobile app securely stores JWT tokens using `expo-secure-store` (as `userToken`). The Admin Dashboard must similarly rely on JWT storage in `localStorage` or secure cookies for calling the backend.
* **Core Screens:** The rider interacts with `DashboardScreen` (shows triggers), `PlanSelectionScreen` (dynamic tiers), `PaymentScreen` (Razorpay flow), and `WalletScreen` (payout history).
* **Location Telemetry:** The app actively posts GPS locations to the backend (`POST /user/location`) to enable dynamic pricing and fraud anchoring.
* **API Service (`api.ts`):** The frontend relies heavily on typed interfaces representing active policies (`ActivePolicy`), triggers (`TriggerInfo`), and the dynamic price quotes (`PlanDetail`). You will re-use these exact interfaces in your web application.

## 3. Mandatory Features & Views (What It MUST Have)

The dashboard requires 4 primary pillars:

### A. The Global Command Center (Overview & Metrics)
A real-time overview of the platform's financial and operational health.
* **Key Metrics:** Total active policies, Total premiums collected, Total automated payouts (24h/7d).
* **System Status:** Monitor the `/health` endpoint and explicitly display the **Global Payout Velocity Limit** status (Active vs. Frozen).
* **Live Weather Risks:** Visual indicators of active disruption triggers (Rain, Heat, Storm, etc.) happening *right now*, fetched via `/triggers`.

### B. Fraud & Sentinels Deck (Critical)
Requires deep visibility into the **Level 7 Composite Fraud Engine**.
* **Live Circuit Breaker Status:** Display if `GLOBAL_PAYOUT_FREEZE` has tripped (when >₹50,000 paid in 5 mins). Needs a manual "Unfreeze/Audit" button.
* **High-Risk Ledger:** A table showing users with a `trust_score` below 50 or those flagged by recent triggers.
* **Fraud Auditing:** Ability to click into a flagged user and see *why* they were flagged (e.g., OSRM Kinematic anomaly, Topographical mismatch, API Fail-safe).

### C. Policy & User Management
* **Rider Database:** List of all riders, their `gig_rider_id`, and unified `trust_score`.
* **Policy Ledger:** View of all active, expired, and pending policies.
* **Location Histories:** Map view of a user's recent ping trail to manually verify OSRM/teleportation flags.

### D. Automated Payout Log
* **Settlement Trail:** A feed of all RazorpayX UTRs generated by the `autopay_trigger_scan` scheduler.
* **Failed Transfers:** Logs of payouts that had `status: pending` or failed during the Razorpay initiation.

## 4. How the Backend Actually Works (Under the Hood)

For the frontend team, it is crucial to understand *how* the data moves in the FastAPI backend (`main.py`):

### Database Operations (MongoDB)
The platform uses an asynchronous MongoDB client (`app.mongodb`). Information is heavily schema-less and nested under the `users` collection.
* **Collection:** `users`
* **Core User Document Structure:**
  ```json
  {
    "_id": "ObjectId",
    "email": "rider@gigguard.in",
    "gig_rider_id": "GG-2024-1234",
    "trust_score": 50.0,
    "active_policy": {
       "tier": "standard",
       "status": "active",
       "baseline_latitude": 19.07,
       "baseline_longitude": 72.87,
       "expires_at": "ISODate"
    },
    "policy_history": [...],
    "payout_history": [...],
    "location_history": [
       {"lat": 19.07, "lon": 72.87, "alt": 15, "time": "ISODate"}
    ]
  }
  ```
> **Note:** The backend does not use separate collections for policies or payouts. Instead, it pushes these objects into `policy_history` and `payout_history` arrays inside the **user document**. Aggregating platform-wide metrics will require MongoDB aggregation pipelines.

### The Fraud Engine (Level 7)
Understanding how the backend flags users so you can visualize it in the dashboard:
1. **Topographical 3D Trap:** Checks if the phone altitude matches the actual Open-Meteo elevation.
2. **Network IP Sentinel:** Blocks datacenters, proxies, and non-India IPs.
3. **OSRM Kinematics:** Ensures the rider hasn't traveled at an impossible speed (>100-140 km/h) between location pings.
4. **Temporal Consistency:** Flags bot-like, erratic ping patterns.
5. **Behavioral Consistency:** Flags users who claim >85% of the policies they buy.
6. **API Fog of War:** Adds penalty points if verification APIs fail.
7. **40km Anchor Rule:** Punishes users who "teleport" >40km from their policy activation baseline.

*Vesting Logic:* Users are put into "Cooling Off" based on their Trust Tier (Veteran=4h, Trusted=12h, Neutral=24h, Suspicious=48h) to prevent instant fraud claims.

### Payout & Circuit Breaker Logic
Every 5 minutes, an APScheduler task (`autopay_trigger_scan`) wakes up. It fetches weather, runs the fraud check, and auto-settles via Razorpay. If >₹50,000 is settled within 5 minutes, it sets `GLOBAL_PAYOUT_FREEZE = True` and HALTS operations.

## 5. API Endpoints Map

### Existing Endpoints Extracted from Frontend (`api.ts`) & Backend (`main.py`)
* `GET /health`: Model status, model R2 score, DB connection status.
* `POST /premium`: Dynamic premium calculations based on GPS and active days.
* `POST /triggers`: Live check of real-time active weather triggers.
* `POST /auth/login` & `/auth/register`: Token-based JWT user generation.
* `POST /auth/firebase-sync`: Synchronize Firebase UID tokens with the DB user.
* `GET /auth/me`: Fetch the current user profile, including arrays of active policies and `payout_history`.
* `POST /auth/profile/update`: Modify user details (name, dob, address, active days, etc.).
* `POST /policy/purchase` & `/policy/order`: Handling Razorpay order creations and policy validations.
* `POST /policy/payout/simulate`: Fire an automated trigger settlement via API.
* `POST /user/location`: GPS telemetry injection.

### Missing Endpoints (Backend Implementation Required)
> **CRITICAL WARNING FOR FRONTEND DEVS:**  
> The current API is entirely user-centric. **There are currently NO Admin-specific API endpoints.** 
> To build the dashboard securely, the backend team MUST implement the following (or you must write an internal DB connection layer directly connecting to MongoDB):

1. `GET /admin/stats`: To return aggregated totals (Total users, policies, payouts, total INR spent).
2. `GET /admin/users`: Paginated list of users, filterable by `trust_score`.
3. `GET /admin/users/{id}`: Detailed view of a single user's `location_history` and fraud strikes.
4. `GET /admin/system/circuit-breaker`: Returns the boolean status of `GLOBAL_PAYOUT_FREEZE` and recent 5-min activity.
5. `POST /admin/system/circuit-breaker/reset`: Allows operators to reset `GLOBAL_PAYOUT_FREEZE` after auditing a flash crash.

## 6. Development Roadmap for Frontend

1. **Phase 1: Mock Layouts & Integration Strategy**
   Establish the visual identity of the dashboard. Build out the Global Command Center using mock data while the backend develops the `/admin/*` routes.
2. **Phase 2: Database Visualizations**
   Hook up the map components (Leaflet) and chart components (Recharts) to show policy distributions and rider heatmaps based on the `users` DB structure.
3. **Phase 3: Fraud Intervention UI**
   Build the interfaces for Circuit Breaker overrides and Trust Score manual audits. This is the 'Wow' factor for Hackathon judges!
4. **Phase 4: Real-time Polling**
   Ensure the dashboard polls `GET /health` and circuit breaker statuses every ~10-30 seconds so admins see the "Flash Crash" happen in real time during a demo.
